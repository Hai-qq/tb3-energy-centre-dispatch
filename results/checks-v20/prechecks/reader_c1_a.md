# c1 独立工程判读：能源中心运行约束、计量计费与可判定性

## 阅读范围与结论性质

本报告只读取指定 `c1/visible/instruction.md`、`c1/visible/app/data/` 的五个原始 JSON/CSV，以及该 `app` 内的可见 Python 文件、Dockerfile。未读取父目录中的任务材料、历史、测试、参考解、其他候选或其他读者结果；未联网。以下模型以题面和原始数据为依据，原程序仅用于理解须保留的输出格式和半小时输出的含义，未被当作正确规范，也未运行它来取得“标准答案”。

核心判断是：该题既是逐时段的电、热、冷联供平衡问题，也是带启动费用的整日机组组合问题。明确的错误不只可能出在燃气换算；把低温热和高温热混在一起、允许没有连接的弃热、忽略发动机无功、同一连接同时买电卖电，以及逐半小时贪心选择开停，都可能得到价格便宜但不能按所报方式运行的计划。部分物理细节仍没有充分规定，尤其是吸收机辅机电耗最终进入哪条散热路径，以及变速冷却塔是否允许主动提高供水温度。

下文所有数值均取自上述可见原始文件，或由所列公式直接计算；没有声称已经求出完整最优计划或其最优总价。

## 1. 时间、初始状态与停机

依据：`instruction.md` 对需求、天气和停机的时间基准说明；`status.json`；两份 CSV 的时间戳；`app/dispatch.py` 关于机组输出保持整个半小时的格式说明。

- 计划日期是 **2026-07-21，当地星期二**。需求文件为 48 个半小时，时间戳带 `+01:00`。每时段功率乘 **0.5 小时**才能得到能量，不能把 kW 原样累计成 kWh。
- 必须按同一实际时刻关联天气和需求。当天当地 `00:00` 对应 **2026-07-20T23:00Z**，当地 `23:30` 对应 **2026-07-21T22:30Z**。用天气 UTC 字符串的日期前缀截取 7 月 21 日，会错位一小时；行数仍然是 48，不能用行数相等证明对齐正确。
- 电价和停机按当地钟表时间。星期类型也应按当地计划日期判断。当天 UTC 日期换算误用虽仍可能得到工作日费率，但换到周一、周六等边界日就会改变费率。
- GE1 在 `07:00–11:00` 不可运行，即通常按左闭右开解释，07:00 到 10:30 的八个半小时为零，11:00 可再次投入。B2 整日停机，必须输出为零。
- 停机信息是“plant”的停机，不是只对发动机生效的规则。其他日若 EC、AC、PV 或某个塔单元停机，也应限制对应设备；某个塔停机会减少可用塔单元数。
- 若未来停机端点落在半小时内部，而输出必须保持整个半小时，不能仅检查时段起点是否可用。任何正长度重叠都会使该时段持续正输出与停机冲突。跨午夜停机的文本表示规则未在材料中详细定义，当天没有这类歧义。

`running_at_midnight = [GE1]` 的通常机组组合读法是日初边界已有 GE1 在运行，因此它延续运行不收费；GE2 在首时段开机应收费。没有最短运行时间或停机时间数据，不能据此额外要求 GE1 必须继续运行一整段。若出题方希望“午夜在运行”直接锁定第一时段状态，而非作为上一状态参与启动计数，需要明确这种不同含义；这会改变可选计划。正常边界状态读法下，允许在 00:00 停止 GE1，但当天没有停止费用。

## 2. 发动机：机端电功率、分段曲线与开停

依据：`plant.json.engines`，以及题面“表格点间线性、端点外平坦，发动机点从最小到额定输出”的说明。

令 `u_i,t` 表示运行状态，`p_i,t` 表示所报的发动机机端有功输出：

- GE1：关闭时 `p = 0`；运行时 `600 ≤ p ≤ 1200 kWe`。
- GE2：关闭时 `p = 0`；运行时 `400 ≤ p ≤ 800 kWe`。
- 运行时 GE1、GE2 分别有 32、24 kWe 固定辅机用电；停机时本题没有给出待机电耗。
- 燃料、高温热、低温热必须分别在相邻表点间插值，不能把首末点连成一条覆盖全范围的直线，也不能用不相邻点任意混合。发动机关闭是独立状态，不能拿“表外平坦”解释为零发电仍消耗最小负荷燃料，也不能运行在零与最小输出之间。

例如 GE1 在 900 kWe 时，原始表给出净热值燃料 2275 kW、高温热 1110 kW、低温热 158 kW。只连 600 与 1200 两端会把燃料算成 2287.5 kW、高温热算成 1062.5 kW；这不是原表。各段斜率如下，足以独立重算：

| 机组、区间 kWe | 净热值燃料斜率 | HT 热斜率 | LT 热斜率 |
|---|---:|---:|---:|
| GE1，600–900 | 1.900000 | 0.916667 | 0.133333 |
| GE1，900–1200 | 1.983333 | 0.600000 | 0.143333 |
| GE2，400–600 | 1.950000 | 0.950000 | 0.135000 |
| GE2，600–800 | 2.100000 | 0.600000 | 0.145000 |

表中每个值均为“相应 kW 增量 / 电输出 kWe 增量”，截距由该段左端原始点决定。

发动机维护费最直接的材料读法，是以表中机端发电量计：GE1 为 £11/MWh(e)，GE2 为 £12.5/MWh(e)，不能把它当 £/kWh，也没有依据改按厂用电扣除后的并网电量计算。启动费是 GE1 £38/次、GE2 £27/次。只在由关到开的边界产生，不在每个运行时段都收费。没有给出启动燃气、热机/冷机费用区别、爬坡、最短开停机时长、日末目标状态或次日继续运行价值；不能凭“工程师觉得频繁”自行补入这些数值。

## 3. 电力连接与计费：每条关系的依据

### 3.1 有功平衡

依据：题面对 `demand.csv.electricity_kw` 的范围定义；发动机和吸收机辅机字段；电制冷机 COP；PV 和供电连接数据。

设基础有功需求为 `D_e`，电制冷输出为 `c_1,c_2`，吸收制冷输出为 `a`，实际 PV 有功为 `v`。则并网点净有功输入为：

```text
P_grid = D_e
         + 32 u_GE1 + 24 u_GE2
         + c_1/COP_1 + c_2/COP_2
         + 0.022 a
         - p_GE1 - p_GE2 - v
```

塔风机与泵已经包含在基础需求里，不能再随意加一遍。制冷量是 kW 冷量，不是电输入。锅炉没有给出独立辅机电耗，不能自行增加一个固定比例。

单一连接的进口、出口应由这一个净交换量得到：

```text
import_kw = max(P_grid, 0)
export_kw = max(-P_grid, 0)
```

因此同一时段模型不能把二者作为相互独立、可同时为正的电流。当天夜间进口 7 p/kWh、出口 12 p/kWh；如果任意同时增加 250 kW 买入和卖出，净平衡不变，每半小时却凭空“赚” £6.25。这是错误的松弛模型，而不是医院真的能够采用的经济措施。若要研究半小时内部实际反向电流带来的分向累计电量，需要更细时间数据；现有半小时计划不能凭空创造这种交易。

### 3.2 无功、发电机 kVA 和连接 kVA

依据：题面说 reactive 列为全站除发动机发电机之外的无功；发电机明确 `fixed power factor, overexcited`、功率因数 0.95。

按需求无功为正、发电机过励磁向站内供无功的符号约定：

```text
k = tan(acos(0.95)) = 0.3286841052
Q_generator,i = k p_i
Q_grid = D_q - k(p_GE1 + p_GE2)
S_generator,i = p_i/0.95
```

这不是可自由优化的无功设定值。也不是取正号让发电机增加站点无功需求。reactive 已是上述定义的全站需求，不应再依据电制冷机、辅机或 PV 猜一个功率因数叠加无功。

发电机约束为 `p_GE1/0.95 ≤ 1500 kVA`、`p_GE2/0.95 ≤ 1000 kVA`。在本题现有额定有功上限下，两条发电机 kVA 限制不收紧：满载分别约 1263.158、842.105 kVA；但它们的物理含义与并网点限制不同。

进口时连接约束必须为：

```text
P_grid² + Q_grid² ≤ 1220²,   P_grid ≥ 0
```

不能用 `import_kw ≤ 1220` 代替视在功率限制，也不能先用原始 `D_q` 算一个与机组输出无关的最大进口功率。运行机组会改变可用的有功进口余量。`Q_grid` 可能成为负数，仍须平方，不能裁成零。若 `|Q_grid| > 1220`，把根号里的负数裁成零并宣布允许零有功进口，也不能修复无功越限。

出口明确有 `export_kw ≤ 250` 的有功上限。**在反送时是否还应应用同一个 1220 kVA 圆，是一处文字上的不充分规定**：字段名是 `import_capacity_kva`，可以读为进口合同限制；也可以把题面的“connection limits”理解为共同的连接载流容量。这不是出口 250 kW 可以替代无功校核的问题。应补充出口时适用的连接 kVA／无功限制。对当前日期，这个差别不会形成有效的额外约束：原始无功范围约 201.9–327.3 kvar，总机端有功不超过 2000 kW，因此即使取最大反送 250 kW，可能的净无功绝对值也远低于 1220 kvar，两种限制在反送区均不收紧。

### 3.3 PV

依据：`plant.json.pv.inverter_ac_kw = 280`、对应天气预测、PV 作为发电项的含义。

应使用正确时刻的 PV 预测，实际输出不得为负或超过 280 kW；停机时为零。当日对齐后的最大预测是 266.5 kW，额定截顶没有实际影响。

材料未明说 PV 是固定采用的可用预测，还是允许主动限发的调度变量。若预测超过额定，要知道列值是已经受逆变器约束的 AC 预测，还是仍需裁切的潜在输出；`data.py` 的注释称 AC output，但这种代码注释不能替代一份更明确的数据字典。对当日没有超额预测这一事实，至少无需猜测截顶量。不能无依据允许 PV 超过预测来补电。

## 4. 热路：必须按温度层级与实际连接守恒

依据最关键的是 `instruction.md` 明说 `plant.json` 列出全部设备和热路的每一条连接，而 `heat_circuits` 的连接如下。

| 热路 | 明示来源 | 明示去路 | 对调度的含义 |
|---|---|---|---|
| engine_ht，90/70°C | GE1、GE2 的缸套水与排烟回收 | AC1 generator、PHE1 | 两台发动机 HT 可在吸收机和供热换热器间分配 |
| ge1_lt，40/35°C | GE1 intercooler | LT radiator 1 | 只能交给自身低温散热器 |
| ge2_lt，40/35°C | GE2 intercooler | LT radiator 2 | 同上；不能挪作 HT 或楼宇热 |
| lthw，80/60°C | PHE1、B1、B2 | hospital buildings，另有 75 kW 损失 | 建筑需求是末端热量，供入回路须多覆盖 75 kW |
| condenser_water | EC1、EC2 冷凝器，AC1 absorber/condenser | CT1、CT2 | 制冷系统排热受塔能力约束，不是发动机 HT／LT 的任意备用去路 |

令 `H = HT_GE1(p_GE1)+HT_GE2(p_GE2)`，`f ≥ 0` 为 PHE1 传给 LTHW 的热量，`b_1,b_2 ≥ 0` 为锅炉热输出。没有列出额外 PHE 损失或容量，现有可计算模型是：

```text
H = f + a/0.71
f + b_1 + b_2 = D_heat + 75
0 ≤ b_i ≤ boiler_i.max_kw
```

消去 `f` 后，既要有总热量等式，也要有非负、方向正确的换热流：

```text
H - a/0.71 + b_1 + b_2 = D_heat + 75
a/0.71 ≤ H
b_1 + b_2 ≤ D_heat + 75
```

这些关系意味着：

1. **LT 不能与 HT 相加作为可利用热量。** 40°C 的低温回路不仅温度不足，而且物理去路只列了散热器。
2. **锅炉不能直接或倒流经 PHE1 给 AC1 提供热量。** 锅炉只进入 LTHW；该回路 80°C 也低于 AC1 的 85°C 最低热水入口要求。AC1 的已列热源是 90°C 发动机 HT。
3. **不能用一个“供热 ≥ 需求”的不等式默认多余 HT 可以任意弃掉。** 这里没有 HT 散热器、HT 到冷却塔支路、储热装置或额外热用户。完整热路的字面模型要求已产生的 HT 沿已列出口全部找到去路，楼宇也不能被当成无上限的弃热负荷。
4. LT 散热器确实列出了去路，因此 LT 热可排掉；但材料没有给散热器随干球温度变化的散热容量或电耗，无法另外证明现实世界散热器的极端天气能力，也不能自创此类约束。

关于第 3 点：工程上“可回收热功率”有时可以只是上限，实际装置可能有排烟旁通或应急散热。因此读者可能想到允许不用 HT；但是本题数据把 HT 当作分段性能输出，同时特意声明热路连接完整，没有提供可调回收比例、缸套水与排烟可旁通比例或任何对应去路。**这不是与等式模型同样受当前文字支持的自由选择。** 如果确实希望允许弃热，题面必须补充那条设备／连接、容量和热回收调节的含义。也不能因为真实 CHP 通常有应急设备，就替此题偷偷加设备。

PHE1 未给温差约束、效率或额定容量。当前能做的是采用列出的温度和守恒，并不施加未知的数值损失或上限；这应被理解为材料的简化，而不是已经证实真实 PHE 无穷大、绝对无损。

## 5. 制冷、冷却水与塔排热

依据：三种制冷设备的额定冷量、COP 表，塔的湿球性能表及上述冷凝水连接。

```text
c_1 + c_2 + a = D_cooling
0 ≤ c_1 ≤ 1400,  0 ≤ c_2 ≤ 1000,  0 ≤ a ≤ 800  (kW cooling)
W_EC1 = c_1/COP_1(T_cw)
W_EC2 = c_2/COP_2(T_cw)
H_AC = a/0.71
W_AC_aux = 0.022 a
```

停机和水温条件会进一步把相应设备可用上限限制为零。COP 应在“冷凝器入口水温”表中插值，不能拿干球温度直接查 COP，也不能把湿球温度直接当入口水温。常规供水估计是：

```text
T_cw,lowest = max(wet_bulb + 4, 21) °C
```

塔排热能力是**可用塔单元数**乘按湿球温度插值的每单元能力，表外按题面取端点值。当前两单元都可用；当天湿球为 18.4–20.6°C，对应塔能力 3435.0–3077.5 kW。最低供水估计为 22.4–24.6°C，全部高于 AC1 的 22°C 冷却水最低入口要求，发动机 HT 90°C 也高于它的 85°C 热水最低要求。因此本日期没有“过冷导致 AC 不可用”的争议。

冷却塔承担的是**排热**：电制冷机至少要排掉冷量与压缩机电输入之和，吸收机至少排掉冷量与热驱动输入之和。标准简化式为：

```text
R = c_1 + c_1/COP_1
    + c_2 + c_2/COP_2
    + a + a/0.71
R ≤ available_tower_capacity(wet_bulb)
```

只将总冷量与塔容量比较，会遗漏真实的压缩功和吸收机热输入。

**仍需说明的两处细节：**

- **AC 辅机电耗的热去向。** 如果 0.022a 的全部电功最终在吸收机的 absorber/condenser 冷凝水回路变热，上式应再加 `0.022a`。如果该字段包括向机房散热的电机、控制器或其他独立辅助设备，则不一定全部进入塔。原文未给这些辅机的组成和散热位置。电力平衡必须加这项是确定的；塔排热是否全量加这项仍有两种工程上合理读法。AC 满负荷时差 17.6 kW，不能只凭字段存在就假装知道去路。严格追求“每个数字与实际装置一致”，应补充这项定义。
- **冷却水温是固定公式还是可调设定值。** 塔标明变速风机，`min_leaving_water_c` 也是“最低”温度，常见控制可以降低风量、把供水保持得更暖。冷天时可以读成固定 `max(wb+4,21)`，于是低于 22°C 就禁用 AC；也可以读成可控下限，开 AC 时把设定值提高到至少 22°C，相应降低电制冷机 COP。后一读法在工程上合理，但资料未明确调温的可行范围、方式、对排热能力及已预测风机电耗的影响。当前日期两种最低目标一致；工具须适用其他日期，这个定义依然有必要补全。

例如 15:30，当地湿球 20.5°C，冷量 1780.2 kW，按 24.5°C 水温查得 EC1 COP 5.9375、EC2 COP 4.825，塔容量 3093.75 kW。若 AC 输出 800 kW，剩余 980.2 kW 全给 EC1，则排热不含／含 AC 辅机分别约 3072.047／3089.647 kW；同样冷量若全部给 EC2，则分别约 3110.111／3127.711 kW，均超过塔容量。两种计划冷量相同，塔可行性不同，说明不能只检查“冷量达标”。这个算例只核算排热，不声称构成经济最优安排。

## 6. 燃气计量与账单成本：方向可以唯一确定

依据：发动机 `fuel_basis = net CV`；锅炉 `efficiency_basis = gross CV`；燃气 `billing_basis = gross CV`，`gross_to_net_cv_ratio = 1.108`，价格 4.35 p/kWh。

同一物理燃气量的 gross CV 能量比 net CV 能量大 1.108 倍。发动机表中净热值功率换到账单热值必须**乘以 1.108**：

```text
G_engine,billed_kw = 1.108 F_engine,net_kw(p)
G_B1,billed_kw = b_1/0.905
G_B2,billed_kw = b_2/0.83
gas_kwh,t = 0.5 [1.108(F_GE1 + F_GE2) + b_1/0.905 + b_2/0.83]
```

锅炉效率已按 gross CV 定义，不应再次转换。当天 B2 停机，它的项必须为零。

GE1 600 kWe 运行半小时，发动机燃气应为 `1705×1.108×0.5 = 944.570 kWh`，相应燃气费 £41.088795。若反而除以 1.108，会报 769.404 kWh，比正确结果低约 **18.544%**。这个方向错误本身就与“发动机运行日燃气预测明显偏低”的症状吻合；它并不说明修正这个比例就修好了全部调度问题。

这份输入足以计算按 gross CV 计费的燃气 kWh，不能计算燃气表体积读数 m³，因为没有给单位体积热值、温压／压缩系数等。原程序输出明确要的是 billed kWh，所以不必发明一个体积换算。

当日当地电价为：

| 当地时段 | 进口 £/kWh | 出口 £/kWh |
|---|---:|---:|
| 00:00–07:00 | 0.070 | 0.120 |
| 07:00–16:00 | 0.226 | 0.120 |
| 16:00–19:00 | 0.415 | 0.120 |
| 19:00–24:00 | 0.226 | 0.120 |

逐时段总成本应按实际输出独立重算：

```text
cost_t = 0.5 [import_rate_t × import_kw_t − 0.12 × export_kw_t]
         + 0.0435 × gas_kwh_t
         + 0.5 [0.011 × p_GE1,t + 0.0125 × p_GE2,t]
         + 38 × start_GE1,t + 27 × start_GE2,t
```

其中 `start_i,t = 1` 当且仅当从上一状态的停机变为本时段运行；日初上一状态通常由 `running_at_midnight` 给定。启动次数的 summary 必须与逐时段这项费用完全一致。材料没有需量费、无功罚款、燃气固定费或税项；不能擅自把它们加进可比较的调度目标。“按账单计价”在本题范围内是使用明示费率和热值基准，并不等于已取得现实合同所有账单条款。

## 7. 当天可直接推出的有力检查

以下都不依赖原优化器是否正确。

1. **每个半小时至少运行一台发动机。** 正确对齐后，全日 `基础有功需求 − PV预测` 的最小值已经是 1229.0 kW，高于进口连接 1220 kVA 所能承受的任何有功值；尚未计入制冷和新增辅机电耗。因此“全停机、全靠网电”的任一时段都不成立。GE1 07:00–11:00 检修，故这八段 GE2 必须运行。
2. **B2 全天为零。** 这不能因为 B1 效率更高、经济模型通常自然不选 B2，就省掉停机约束。
3. **午夜两台发动机同时开到最低负荷也不满足热路。** 两机最小 HT 为 `835+590 = 1425 kW`。00:00 建筑加损失为 `250.3+75 = 325.3 kW`；即使全部 469.7 kW 冷量都给吸收机，最多消耗 `469.7/0.71 ≈ 661.549 kW` HT，因此已列去路最大总消纳为 **986.849 kW**。没有 HT 弃热支路时，两机同开不能成立。
4. **同一时段 GE1 也不能随意提高到 900 kWe。** 若它独开，90°C 热路最多同样消纳 986.849 kW，按其 600–900 kWe 段曲线，输出最高约 **765.654 kWe**。GE1 在最低 600 kWe 时，即使锅炉为零，至少须供 AC1 **361.887 kW** 冷量才能消纳 HT；若 GE2 最低负荷独开，对应最低吸收冷量是 **187.937 kW**。
5. **午夜网电限额不能按原始有功看。** 当地 00:00 的湿球 18.6°C，对应供水 22.6°C、EC1 COP 6.365。若全用 EC1，且没有机组，基础需求加制冷电耗约 1330.494 kW，原始无功 213.1 kvar 时最大允许有功进口约 1201.245 kW，明显越限。机组投入后，必须重算无功，不能沿用这个 1201.245 作为固定上限。
6. **输入的日能量核对值**：基础有功需求 37298.350 kWh；建筑热需求 8440.950 kWh，75 kW 管网损失另为 1800 kWh；冷需求 24349.050 kWh；正确时刻 PV 预测合计 2466.600 kWh。它们是输入汇总，不是最终购电量、燃气量或最优成本。

上述结论不能唯一推出“哪台发动机应在所有非检修时段运行”或精确日总价。判断那些结论需要按完整约束优化，并先明确会影响结果的建模细节。

## 8. 如何判断一份计划既正确又经济

### 8.1 先独立验证所有可执行量

应读取所交付 JSON 的实际数值，而不是只相信它自己的 `grid_ok` 或优化器状态：

- 日期与 48 个当地时段无重复、遗漏、错序；设备字典覆盖全部所要求的设备。
- 从输出反推每台机组的开停状态，验证停机、最小负荷、额定输出、发电机 kVA，以及各制冷／锅炉上限。
- 用原表相邻点重算每台发动机燃气、HT、LT；用正确天气和水温重算 COP 与塔能力。
- 独立检查有功平衡、无功净交换、连接限制、买卖互斥、供冷等式、HT 分配、PHE 方向、楼宇供热加损失及塔排热。
- 用这些相同输出重算 billed gas、分时购售电、维护费、启动费和总费用。
- summary 的能量、费用、启动次数、`grid_ok` 都与逐段结果一致。`grid_ok` 只能说明电连接是否满足，不能代表热、冷、停机等约束都满足。

格式原本会将浮点数保留三位小数。要确保舍入后的计划仍在说明的数值容差内可行，尤其是贴着连接圆、HT 等式或塔容量的解。若 summary 从未舍入数值汇总、行值各自舍入，二者会有小幅舍入差；验收应有明确且很小的容差，或统一计算与发布方式。不能让“舍入”成为实际越限或燃气、费用明显不符的借口。

### 8.2 再证明是整日最低成本

只比较每个半小时的运行费不足以证明经济性。启动费连接相邻时段：眼前更便宜的机组切换可能得不偿失。常规最优目标是一天的上述 `Σ cost_t`，不是最低燃气、最低碳排、最大 CHP 发电量或单独最少启动次数。

本材料只给启动费用作为跨时段耦合，所以一种清楚的求解结构是：

1. 对每时段和两台发动机的四种开停组合，求该状态真正最低的可行运行费用；不可用的状态记为不可行。
2. 发动机两段性能必须分别精确处理，进口／出口方向也应分别处理；每个固定分段、固定方向的子问题中，有功、热、冷量关系是线性的，而固定功率因数带来的连接圆约束不能被错误地当成固定进口 kW 上限。
3. 在 48 个时段的四状态序列上做含初始状态的动态规划，状态转换加相应启动费，然后回溯全日序列。由于没有其他已给出的时间约束，在每状态内先取最低运行费、再做状态动态规划，不会遗漏已规定的未来影响。

这说明为什么全日问题可以高效求解，并不意味着任意一个声称成功的局部优化就证明了最低成本。连续子问题也要给出可行、足够准确的最优结果；若采用对连接圆的近似，须检查真实圆约束并说明成本误差，而不是只检查近似限制。

完整验收应至少同时有：独立物理重算通过；按真实计费重算通过；整日目标与可靠的全局下界／穷尽分段状态优化结果在声明容差内一致；同样输入重复运行得到同样计划。在可能存在并列最优时，允许选择任意一个可重复的最优解，但不能把某个任意的具体开停序列当成题面唯一答案。Python 3.13、仅 NumPy/SciPy、两分钟内完成也是明示要求；不能把只在这一天硬编码得到的输出当成修好的每天运行工具。
